# Гайд: отдать проект агенту под ключ (луп + субагенты + mise)

Эксперимент, а не производственный процесс. Цель — не «получить продукт», а **посмотреть, где агент ломается**, и получить это на бумаге.

Область действия: репозиторий `simple-key-store`. Источник правды — `secrets-spec.md` (rev 2) и `sqlite-storage-plan.md`. Этот файл описывает, как запустить по ним автономный луп. Он не заменяет спеку и не переопределяет её.

Главный принцип всего гайда:

> **Агент не голосует за готовность.** Готовность определяет единственная команда — `mise run check`. Всё остальное (отчёт агента, «я всё сделал», зелёный вывод в чате) является показанием подсудимого, а не доказательством.

---

## 0. Что это и чего это не делает

Делает: один агент-оркестратор идёт по дорожной карте M1–M4 из §12 спеки, привлекая субагентов для разведки, реализации и независимой проверки. Внешний луп останавливается по жёсткому условию. Весь прогресс живёт в git и `ATTEMPTS.md`, не в контексте сессии.

Не делает: не даёт агенту права менять модель угроз (§1) и anti-scope (§14), пушить, деплоить на бокс, ослаблять тесты. Эти границы не «пожелание» — см. §5 про их реальную жёсткость.

Что считается успехом эксперимента: таблица из §7, заполненная по факту. Что считается провалом: агент объявил победу при красном гейте, и вы это проглотили.

## 1. Предполётный чек

Прогоняется **до** первого запуска агента. Пункты 1–4 — руками и один раз, они не работа агента.

1. **Спека перестаёт быть черновиком.** В `secrets-spec.md`: `Статус: черновик к реализации` → `Статус: контракт, rev 2`. Агент, читающий «черновик», справедливо считает себя вправе переписать содержание. Сначала снимите эту двусмысленность.

2. **Рассинхрон версии Go.** Спека §9 говорит «Go 1.27», `mise.toml` пиннит `go = "1.26.5"`, `go.mod` — `go 1.26.5`. Приведите к одному. Пока рассинхрон жив, агент потратит итерацию на «почини несоответствие», причём не зная, какая сторона права.

3. **Пустой файл.** `internal/cli/sksd/main.go` — 0 байт. Это не «заглушка», это синтаксическая ошибка: `go build ./...` на нём падает. Либо удалить, либо положить минимальный `package main` с `func main() {}`. Ломающийся с нуля билд обесценивает гейт.

4. **Гейт зелёный на чистом дереве.** Прежде чем запускать луп, `mise run check` должен проходить на текущем коммите. Иначе первая же итерация начнётся с красного гейта, который агент не создавал, и весь бюджет уйдёт на разбор чужого долга. Если тесты ещё не написаны — заведите таски, сформулируйте, что они должны проверять, и добейтесь хотя бы того, чтобы `check` был честно зелёным (пусть на малом числе тестов). Врать нельзя: таска-заглушка `run = "true"` запрещена, см. §7.

5. **Открытые решения §13 — агенту.** По вашему решению из §13 спеки агент отвечает сам. Требование к нему — не «решить», а **зафиксировать**: каждое из семи решений попадает в `DECISIONS.md` с обоснованием до того, как начнётся код, который от него зависит. Решение, принятое молча внутри реализации, считается нарушением, а не оптимизацией.

6. **Рабочая копия чистая, ветка своя.** `git status` пуст, ветка `agent/full-handover` (или подобная). Это нужно, чтобы потом можно было посмотреть `git log` как хронологию эксперимента, а не спасать разбросанные по дереву правки.

7. **Утвердить с командой эксперимента, что агенту разрешено делать без спроса:** добавить зависимость, изменить схему БД, переименовать пакеты. Всё это он будет делать, и вы не должны узнать об этом после факта. Список — в §5.

## 2. mise: депенденси и таски

### 2.1. Граница ответственности

Важно не спутать: **mise не управляет зависимостями Go.** Го-модули — это `go.mod`/`go.sum` и `go mod tidy`. mise управляет **инструментами** (toolchain, линтеры, утилиты для интеграционных скриптов) и **тасками** (единообразные команды). Таски-обёртки над `go mod` — да, но сам резолвинг версий модулей остаётся за Go.

Что это значит на практике:
- `mise install` из чистого клона даёт ровно тот Go и ровно те линтеры, что нужны. Версия Go перестаёт быть «у меня локально собралось».
- `go mod download` заворачивается в таску, чтобы агент не изобретал флаги.
- Если понадобится `sqlite3` или `jq` для интеграционных скриптов — они тоже в `[tools]`, а не в README как «установите у себя».

### 2.2. `[tools]`

Заменить текущий `mise.toml` (в нём сейчас только go и одна таска `client`):

```toml
[tools]
go = "1.26.5"                 # согласовать со спекой §9 и go.mod
golangci-lint = "1.64.7"      # версия уже стоит в системе
staticcheck = "2024.1.1"
gopls = "latest"              # чтобы агент ходил в определения, а не угадывал

[tasks.client]
run = "go run ./internal/cli/sks"
```

Правила:
- **Версии пинятся**, `latest` — только для чисто-инструментального (форматтеры, LSP). Плавающий линтер = гейт, который сегодня зелёный, а завтра красный без изменений в коде. Это отравляет метрику эксперимента.
- `aqua:`-префикс, который уже используется в конфиге системы для многих тулов, — нормальный вариант; главное, чтобы версия была явной.
- Ни одной интерактивной таски. Луп не умеет отвечать на вопросы.

### 2.3. `[tasks]` — целевой набор

```toml
# --- зависимости ---
[tasks.deps]
run = "go mod download"

[tasks.tidy]
run = "go mod tidy && git diff --exit-code go.mod go.sum"

# --- формат и статика ---
[tasks.fmt]
run = "go fmt ./..."

[tasks."fmt:check"]
run = "test -z \"$(gofmt -l .)\" || { gofmt -l .; exit 1; }"

[tasks.vet]
run = "go vet ./..."

[tasks.lint]
run = "golangci-lint run ./..."

[tasks.static]
run = "staticcheck ./..."

# --- тесты ---
[tasks.test]
run = "go test ./..."

[tasks."test:race"]
run = "go test -race ./..."

[tasks."test:cover"]
run = """
go test -race -covermode=atomic -coverprofile=cover.out ./...
go tool cover -func=cover.out | tail -1
"""

[tasks."test:integration"]
depends = ["fmt:check"]
run = """
./scripts/sync-conflict-test.sh
./scripts/no-plaintext-test.sh
"""

# --- сборка ---
[tasks.build]
run = "go build ./..."

# --- гейт ---
[tasks.check]
depends = ["fmt:check", "vet", "lint", "test:race", "test:integration", "build"]
```

Замечания по конкретике:
- `depends` в mise запускает зависимости параллельно; порядок между ними не гарантирован. Если `sync-conflict-test.sh` требует собранных бинарей, соберите их **внутри скрипта** (`go build -o "$tmp" ./cmd/...`), а не полагайтесь на `build`.
- `tidy` с `git diff --exit-code` — потому что «агент добавил зависимость в импорт, но забыл `go mod tidy`» и «агент отредактировал `go.sum` руками» должны падать оба.
- `ci` из спеки §10 (`go vet && go test -race`) полностью перекрывается `check`. Не заводите `ci` отдельно — два гейта разойдутся, и вы будете спорить, какой из них настоящий.

### 2.4. `mise run check` — единственный гейт

Одно имя знают и агент, и луп, и вы. Если гейт нужно расширить — вы добавляете таску в `check`, а не пишете новую проверку в скрипте лупа. **Скрипт лупа не содержит критериев готовности** — только вызов гейта.

## 3. Тест-suite «на все»

### 3.1. «На всё» уже определено

Не надо изобретать понятие полноты: §11 спеки — это готовый Definition of Done («Тест-план (что должно быть доказано)»). Задача гайда — смапить его на таски и не дать агенту самовольно сузить область.

Считается покрытым только то, что есть **все** из: (а) тест существует, (б) тест падает при внесении дефекта в проверяемый код, (в) тест выполняется гейтом.

Пункт (б) — ключевой и его легко пропустить. Тест, который проходит и на сломанном коде, — это не тест, а декорация. Один раз за эксперимент стоит попросить verifier-субагента проверить несколько тестов на «убиваемость» (см. §4).

### 3.2. Матрица: пункт §11 → таска

| Что доказывается (§11) | Где живёт | Таска |
|---|---|---|
| store: set→get возвращает исходное значение | `internal/store/*_test.go` | `test:race` |
| store: `ErrNotFound` при отсутствии ключа | `internal/store` | `test:race` |
| crypto: nonce уникален, AAD-префикс `local\|` ломает несовместимую запись | `internal/crypto` | `test:race` |
| HLC: монотонность при переводе часов назад, порядок `ms→counter→node_id` — **на fake clock**, не на `time.Now()` | `internal/hlc` | `test:race` |
| Порядок версий одинаков у двух клиентов с разным дрейфом часов | `internal/hlc`, `internal/sync` | `test:race` |
| Конфликты: edit/edit, edit/delete, create/create — по одному, оба значения живы | `internal/sync` + скрипт | `test:race`, `test:integration` |
| Идемпотентность: один `change_id` дважды → одна запись в `secret_history` | `internal/store`, `internal/sync` | `test:race` |
| Офлайн: правка при мёртвом сервере → outbox → sync после подъёма | `scripts/sync-conflict-test.sh` | `test:integration` |
| **Нет plaintext в кэше**: маркер не в `cache.db`, `-wal`, `-shm`, outbox, history, логах | `scripts/no-plaintext-test.sh` | `test:integration` |
| Восстановление ключа: нет `machine.key` → exit != 0 и внятная ошибка; `login --reset-key` поднимает кэш | `internal/config`, CLI | `test:race` |
| Контракт CLI: нет ANSI при pipe, `export \| sh -n` чисто, нет ключа → exit 2, пустой кэш + мёртвый сервер → stdout пуст и exit != 0 | CLI-тесты, `internal/ui` | `test:race` |
| Восстановление бэкапа: `VACUUM INTO` + restore в копию → `get`/`ls` работают | `secretd` + скрипт | `test:integration` |
| Path-валидация: `[a-z0-9._/-]{1,512}`, без ведущего слэша, lowercase | `internal/store`, CLI | `test:race` |
| Лимиты: значение ≤ 1 MiB, path ≤ 512, ≤ 500 изменений в батче | `internal/api`, `internal/sync` | `test:race` |
| Rate-limit `/v1/auth/login` 5/мин на IP | `internal/api` | `test:race` |
| Права: `cache.db` 600, `machine.key` 600, каталог 700 | `internal/config`, `doctor` | `test:race` |
| `temp_store=MEMORY` установлен на **каждом** соединении | `internal/store` | `test:race` |

Это не исчерпывающий список, а минимальная планка. Агент дополняет его по ходу; **вычёркивать** из него нельзя без записи в `DECISIONS.md`.

### 3.3. Требования к тестам

- **Тест до кода.** По каждому пункту §11 тест пишется раньше реализации. Это единственное, что делает луп самопроверяющимся: иначе агент пишет код и подгоняет тесты под то, что получилось.
- **`-race` обязателен** (спека §9, §11): синк и один writer в SQLite без него недоказуемы. `test` без `-race` — для быстрой локальной петли, в гейт идёт только `test:race`.
- **Fake clock для HLC.** Спека §9 прямо требует интерфейс `clock`, а не `time.Now()`. Тест, который спит реальным временем, — флаки в CI и ложные метрики.
- **Интеграционные скрипты изолированы по каталогам.** `sync-conflict-test.sh` поднимает сервер в фоне и двух клиентов в `mktemp -d` с `HOME`/`XDG_*`, переопределёнными внутрь временного каталога. Скрипт, который пишет в настоящий `~/.local/share/secrets`, — это не тест, а инцидент.
- **Скрипты возвращают ненулевой код.** Скрипт, который печатает FAIL и выходит с 0, гейт не остановит.
- **`no-plaintext-test.sh` ищет бинарным grep** (`rg -a` / `grep -a`) — иначе совпадение в бинарной БД просто не найдётся, и тест будет ложно зелёным.

### 3.4. Порог покрытия

Соблазн поставить `-coverprofile` с порогом «80%» — понятен и вреден. Метрика покрытия измеряет исполненные строки, а не проверенное поведение; она гонится за геттерами и обходится тестами без `assert`.

Правильно: порог покрытия — **не критерий готовности**, а сигнал. Заведите `test:cover` и смотрите его в отчёте эксперимента. А критерий готовности — построчная выполнимость матрицы §3.2 плюс пункт (б) из §3.1.

Единственное место, где числовой порог уместен: если вы хотите запретить регресс покрытия между итерациями. Тогда сравнивайте с предыдущим значением, а не с абсолютной цифрой.

## 4. Субагенты: роли и границы

Конкретное расширение для делегирования вы выберете сами; здесь — инварианты, которые держат луп осмысленным независимо от инструмента. Если ваше расширение умеет только «передать задачу в дочернюю сессию» — этого достаточно.

### 4.1. Зачем они тут вообще

Две причины, обе не косметические:

1. **Изоляция контекста.** Оркестратор, который прочитал 25 KB спеки, историю правок и свой же вывод, деградирует. Разведка и реализация в свежих контекстах сохраняют качество на десятой итерации.
2. **Независимая проверка.** Автор кода не может проверять свой код: тот же контекст, те же допущения, то же слепое пятно. Verifier обязан быть **другим агентом с чистым контекстом**, получившим задание, спеку и дифф — но не переписку и не оправдания автора.

### 4.2. Роли

| Роль | Права | Задача | Когда вызывать |
|---|---|---|---|
| **scout** | только чтение | разведка: где живёт код, точки входа, поток данных, риски, что в проекте уже есть | перед планированием каждой новой области; «посмотри, нет ли уже готового в `internal/*`» |
| **worker** | пишет код и тесты | реализация одного пункта плана | по одному пункту за раз, а не «сделай M1» |
| **verifier** | только чтение | независимая проверка: соответствие спеке, edge cases, убиваемость тестов, простота | после каждого worker, свежим контекстом |
| **oracle** | ничего не пишет | второе мнение по решению, если выбор кажется рискованным (схема, модель конфликтов, крипта) | на развилках, а не «на всякий случай» |

### 4.3. Жёсткие правила

1. **worker не правит тесты, проверяющие его работу.** Если worker изменил файл теста — это отдельный коммит с отдельным сообщением и отдельным объяснением, которое видно в `git log`. Правка теста «потому что не сходится» = саботаж гейта, и её нужно видеть, а не обнаруживать постфактум.
2. **verifier не пишет вообще.** Его вывод — отчёт, а не дифф. Разрешены мелкие правки только если вы явно доверяете ему это; по умолчанию — нет.
3. **Параллельные worker'ы — только в изолированных рабочих копиях** (git worktree или отдельные копии дерева). Иначе они перетирают друг друга, и вы получаете коммит, который собирается только целиком, но никем по отдельности не проверен. Если ваш инструмент не умеет изоляцию — не запускайте параллельно, идите последовательно.
4. **Один worker = один пункт плана.** Пункт вида «M1 целиком» — это не задача для субагента, это способ получить голословный отчёт.
5. **Субагент получает: спеку (или нужные её разделы), своё задание, состояние гейта.** Не получает: свою прошлую переписку с оркестратором, оправдания, «осталось чуть-чуть».
6. **Бюджет.** Задайте лимит: суммарное число запусков субагентов на итерацию и на весь прогон. Без бюджета луп склонен к бесконечному уточнению мелочей вместо продвижения по M1–M4.

### 4.4. Внутренний луп (review loop)

Схема на одну задачу:

```
worker → verifier → (если замечания) worker → verifier → ...
```

- Максимум **3 раунда**. Если после третьего verifier всё ещё находит проблемы — задача не «почти готова», а плохо сформулирована или архитектурно не решена. Останавливайтесь и разбирайтесь руками.
- Verifier на каждом раунде **свежий**. Переиспользование того же контекста ведёт к «согласию» вместо проверки.
- Verifier сравнивает с **спекой**, а не с реализацией. Формулировка задания: «прочитай §4 и §11 спеки, затем проверь, что реализация доказывает каждое требование».

## 5. Автономия: что решает сам, где встаёт

### 5.1. Решает сам и фиксирует

- Все семь открытых решений §13 (ключ сервера, иерархия путей, права токенов, домен/порт, теги/поля, `secrets run`, rollback).
- Структура пакетов внутри `internal/*`, имена типов, разбиение по файлам.
- Схема БД и миграции — в рамках §2 спеки.
- Добавление зависимости — при условии, что она проходит §9 (никакого cgo, `modernc.org/sqlite`, а не `mattn/go-sqlite3`) и попадает в `go.mod` через `go mod tidy`, а не руками.

Каждое такое решение → строка в `DECISIONS.md` **до** кода, который от него зависит.

Формат (ADR-лайт):

```markdown
## D-3: клиентский кэш шифруется ключом из файла рядом с БД
Дата/итерация: i4
Решение: machine.key лежит в ~/.local/share/secrets/, права 600.
Альтернативы: (а) пароль/unlock, (б) ключ в keyring.
Почему: спека §1 rev 2 уже зафиксировала модель угроз «защита от rg, не от атаки».
Если станет неприемлемо: только клиентская крипта с паролем (возврат к (а)).
Затронутые пункты спеки: §1, §5.
```

Обратите внимание на две последние строки. «Почему» и «если станет неприемлемо» — то, что отличает записанное решение от оправдания.

### 5.2. Обязан остановиться и спросить

- `git push`, открытие PR, теги, force-push.
- Деплой на бокс: systemd, Caddy, `~/apps/secrets/`, любые действия на другой машине.
- Любая запись секретного значения в репозиторий, в лог, в вывод команды или в `DECISIONS.md`/`ATTEMPTS.md`.
- Изменение §1 (модель угроз) и §14 (anti-scope) спеки.
- Ослабление или удаление теста; удаление пункта из матрицы §3.2; сужение уже заявленного поведения.
- Разрушительные операции с данными: удаление `~/.local/share/secrets/`, `~/apps/secrets/data/`, что угодно с `rm -rf` вне `mktemp -d`.
- Добавление cgo-зависимости или чего-либо из §14.

### 5.3. Насколько это жёстко на самом деле

Честно: правила из §5.2 — это политика, а не механизм. Агент, у которого есть bash, технически может сделать всё перечисленное. Реальные защёлки:

- **Нет credentials** — тогда push и деплой физически невозможны. Самый надёжный вариант, и он бесплатный.
- **`pre-push` хук**, падающий с ненулевым кодом. Одна строка, работает без вашего участия.
- **Отдельный пользователь / контейнер** без доступа к `~/.ssh`, `~/srv`, `~/apps`. Если эксперимент того стоит — стоит и это.

Всё остальное — надежда на послушание. Не путайте её с контролем.

## 6. Луп

### 6.1. Внешний: итерация = milestone

Одна итерация — один пункт дорожной карты §12 (M1 → M2 → M3 → M4), внутри — сколько угодно внутренних раундов из §4.4.

Почему не «атомарная задача в итерации»: M1 (§12) — это вертикальный срез «замена `.zshenv` без сети», у него свой DoD (совпадающий набор переменных, `sh -n` чист, grep-тест пуст). Дробить его на «сделай store», «сделай crypto» бессмысленно: пока срез не собран, ни один из кусков не проверяем.

### 6.2. Псевдокод луп-раннера

```bash
#!/usr/bin/env bash
# loop/run.sh — внешний луп. Гейт здесь только ВЫЗЫВАЕТСЯ, критериев не содержит.
set -uo pipefail

MAX_ITERS="${MAX_ITERS:-15}"
LOG="loop/run.log"
mkdir -p loop

for i in $(seq 1 "$MAX_ITERS"); do
  echo "=== iteration $i ===" | tee -a "$LOG"

  # Свежая сессия каждый раз. Состояние — в git и ATTEMPTS.md, не в контексте.
  pi -p "$(cat loop/mission.md)" >>"$LOG" 2>&1

  # ГЕЙТ. Не агент решает, готово ли.
  if mise run check >>"$LOG" 2>&1; then GATE=green; else GATE=red; fi

  {
    echo "## iteration $i"
    echo "- gate: $GATE"
    echo "- diff: $(git diff --stat | tail -1)"
    echo "- agent claims done: $(grep -c '^STATUS: DONE' loop/claim.txt 2>/dev/null || echo 0)"
  } >> ATTEMPTS.md

  git add -A
  git commit -m "loop: iteration $i (gate=$GATE)" >/dev/null 2>&1

  # Стоп-условие: гейт зелёный И агент объявил дорожную карту исчерпанной.
  # Оба условия обязательны: зелёный гейт сам по себе не значит «сделано всё».
  if [ "$GATE" = green ] && [ -f loop/ROADMAP_DONE ]; then
    echo "stop: gate green + roadmap done at iteration $i" | tee -a "$LOG"
    break
  fi
done
```

Обязательные свойства этого лупа:

- **Свежая сессия на итерацию.** Контекст оркестратора не переносится; состояние — только git + `ATTEMPTS.md` + `DECISIONS.md`. Это главное, что отличает луп от «одного длинного разговора, который к концу тупеет».
- **Задание (`loop/mission.md`) не меняется между итерациями.** Оно описывает роль, гейт, границы §5.2 и требование обновить `ATTEMPTS.md`/`DECISIONS.md`. Если вы правите mission каждый запуск — вы не запускаете луп, вы рулите вручную.
- **Стоп-условие из двух частей.** Одного зелёного гейта мало: гейт может быть зелёным на пустом проекте. Агент должен явно создать `loop/ROADMAP_DONE`, что заставляет его сформулировать «что закрыто» и увидеть, что осталось.
- **Лимит итераций** и он не «страховка», а часть эксперимента: сколько итераций реально ушло — одна из метрик §7.
- **Коммит на итерацию**, без push. Каждая итерация — точка, к которой можно вернуться и посмотреть `git log --stat`.
- **Лог в файл.** Полный вывод сессии — первичный источник для разбора; чат для этого не годится.

### 6.3. Что агенту запрещено в лупе

- Коммитить при красном гейте. Красный гейт → коммит-нужно-быть-красным фиксирует сломанное состояние; луп должен останавливаться на разборе, а не накапливать долг.
- Править тест, чтобы он прошёл. Это происходит по двум причинам: тест неверен или код неверен. Обе требуют записи в `DECISIONS.md`/`ATTEMPTS.md`, а не тихой правки.
- Расширять область. Обнаружив, что до M1 нужен рефакторинг пакета `store`, — запись в `ATTEMPTS.md`, не рефакторинг.
- Продолжать после третьего раунда verifier без правок с вашей стороны.

## 7. Метрики: удался ли эксперимент

### 7.1. Что измеряем

| Метрика | Как считать | Что означает |
|---|---|---|
| Итераций до M1, M2, M3, M4 | `git log --grep='loop: iteration'` + `ATTEMPTS.md` | реальная скорость на вертикальный срез |
| **Ложное «done»** | сколько итераций, где агент заявил готовность, а `mise run check` красный | ключевая метрика доверия. Считается автоматически: `STATUS: DONE` из `claim.txt` + `gate: red` в `ATTEMPTS.md` |
| Обойдённые тесты | правки `*_test.go`, сделанные worker'ом, а не по требованию verifier | где гейт был обойдён, а не пройден |
| Тесты без убиваемости | число тестов, которые не падают при внесении дефекта в проверяемый код (выборка, ручная) | декоративные тесты |
| Правки спеки | коммиты, трогающие `secrets-spec.md` | где контракт оказался неполным. Каждая такая правка — это дырка в §11/§13 |
| Решения из §13, принятые молча | решения, которых нет в `DECISIONS.md`, но которые видны в коде | нарушение процесса; самое неприятное, потому что обнаруживается поздно |
| Где встал | последняя запись `ATTEMPTS.md` + открытый вопрос | итог эксперимента |

### 7.2. `ATTEMPTS.md`

Append-only, дописывается лупом и агентом. Не переписывается задним числом — иначе это не дневник, а отчёт о достижениях.

```markdown
## iteration 4 — gate: red
- Закрыл D-3 (machine.key рядом с БД) в DECISIONS.md.
- store.Set/Get + envelope AES-256-GCM готовы, тест set→get зелёный.
- no-plaintext-test.sh падает: маркер MARKER-xyz находится в cache.db-wal.
  Гипотеза: temp_store=MEMORY не применяется, т.к. PRAGMA выставляется до
  SetMaxOpenConns(1) на пуле, а соединение берётся позже. Проверяю.
- Не трогал: sync, server, CLI кроме set/get.
```

Полезность этой записи — в последней строке. «Не трогал» — то, что не даёт итерации расползтись, и то, по чему потом видно, где агент срезал угол.

### 7.3. Красные флаги

Ни один из них не обязан означать провал, но каждый обязан попасть в итоговый разбор:

- Гейт зелёный, а тесты удалены, переименованы в `_test.go.bak` или помечены `t.Skip`.
- `check` проходит быстрее, чем на прошлой итерации, без причины.
- Таска-заглушка: `run = "true"`, `|| true` в конце падающей команды, `<cmd> || echo ok`.
- Тесты без `assert`: вызов функции без проверки результата.
- `-race` убран из гейта, «потому что падает».
- Порог покрытия снижен или исключены файлы из подсчёта.
- Правка спеки, «чтобы соответствовала реализации». Особенно §11 — тест-план это обязательство, а не описание того, что случайно получилось.
- `DECISIONS.md` пуст после M1. Значит, решения принимались молча.

### 7.4. Итог

По завершении — один прогон на вопрос: **если бы этот код написал человек, вы бы заметили разницу?** Где именно (структура пакетов, тесты, граничные случаи, крипта)? Ответ на него и есть результат эксперимента, всё остальное — сопутствующие данные.
