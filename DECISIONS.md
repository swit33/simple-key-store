## D1: серверный ключ at-rest — файл `vault.key`, без unseal-пароля

Дата/итерация: i0
Решение: ключ 32 байта в `~/apps/secrets/data/vault.key`, права 600, создаётся `secretsd migrate`/`serve` при первом старте, читается при старте процесса. Unseal-пароля и интерактивного анлока у сервера нет.
Альтернативы: (а) passphrase при старте (unseal); (б) ключ в systemd `LoadCredential`/keyring.
Почему: §13.1 уже предлагает файл; модель угроз (§1) — защита от чтения БД из бэкапа/копии и от случайного `cat`, а не от root на боксе. Unseal-пароль ломает `Restart=always` без оператора, то есть убивает эксплуатацию на боксе (§8, §10).
Если станет неприемлемо: unseal-пароль при старте (возврат к (а)) или `LoadCredential` из systemd — без изменения схемы БД.
Затронутые пункты спеки: §1, §8, §13.1.

## D2: пути иерархические, lowercase

Дата/итерация: i0
Решение: `path` = сегменты, разделённые `/`, как в §2 (`prod/pullmd/token`, `deepseek-api`). Полный алфавит — `[a-z0-9._/-]{1,512}`, lowercase, без ведущего слэша, без пустых сегментов и `.`/`..`. Валидация — одна функция в `internal/store`, общая для CLI и сервера; невалидный аргумент → exit 1, отсутствующий валидный ключ → exit 2, но никогда не запись «как есть».
Альтернативы: (а) только плоские имена (проще парсинг `ls`); (б) иерархия с произвольным регистром.
Почему: §13.2 и примеры §2/§4 уже используют иерархию; `ls --tree` (M1) без неё бессмысленен. Lowercase + фиксированный алфавит убирает регистровые коллизии на macOS (HFS+/APFS) и упрощает mapping в env-имена (D13).
Если станет неприемлемо: плоские имена (а) — миграция тривиальна, `path` остаётся строкой PK.
Затронутые пункты спеки: §2, §6, §13.2.

## D3: обычный enroll-токен машины — read/write; read-only поддерживается; админ-операции с токенами — только loopback

Дата/итерация: i0
Решение: токен, выданный при enroll, по умолчанию read/write — иначе указанный в §12 клиент (`set`/`sync`) не может выполнить свою работу. Явный флаг `--read-only` поддержан (колонка `tokens.read_only` из §2) и проверяется на сервере для всех write-эндпоинтов. Управление токенами (`token add|list|revoke`, `/v1/tokens`) доступно только с loopback и **не** проксируется Caddy.
Альтернативы: (а) read-only по умолчанию, как предлагает §13.3; (б) роли/RBAC (запрещено §14).
Почему: §13.3 — открытый вопрос, а не контракт; M2/M3 требуют push из клиента, поэтому read-only-по-умолчанию сделал бы срез неработоспособным. Отдельная роль/ACL — это RBAC, прямо запрещённый §14. Loopback-only для админки сохраняет смысл read-only-токенов: украденный read-only токен не выпускает новых.
Если станет неприемлемо: (а) read-only по умолчанию + отдельный `--write` при enroll; раздачи прав уже хватает в схеме.
Затронутые пункты спеки: §1, §2, §6, §8, §13.3.

## D4: сервер слушает 127.0.0.1:8686; домен подключается только после enroll

## D7: история и diff — в v1; команды `rollback` в v1 нет

Дата/итерация: i0
Решение: `secret_history` заполняется каждым set/delete/resolve (§2) уже в M1–M3; `secrets history <path>` и `secrets diff <path> [--rev N]` входят в v1 (M3). `secrets rollback` не реализуем: откат делается явным `set` старого значения (его печатает `history`/`diff`).
Альтернативы: (а) `rollback <path> --rev N` в v1 (§13.7); (б) не хранить историю до v2.
Почему: §13.7 — открытый вопрос. История — дешёвая запись при каждом write и нужна для `diff` (M3); `rollback` — это ещё один write-путь со своей семантикой конфликтов (rollback к версии, которую кто-то уже перезаписал) и с риском молчаливой перезаписи, запрещённой §4.6.
Если станет неприемлемо: `rollback` как сахар над `set` (взять старое значение из `secret_history` и отправить обычным изменением) — модель конфликтов не меняется.
Затронутые пункты спеки: §2, §6, §13.7.

## D9: поэтапный гейт — интеграционные таски подключаются по мере появления реальных скриптов

Дата/итерация: i0
Решение: на предполёте `mise run check` = `fmt:check`, `vet`, `lint`, `test:race`, `build`; `test:integration` в `check` пока **не** входит, потому что `scripts/*.sh` ещё не существуют. Обязательства по этапам: **M1** добавляет `scripts/no-plaintext-test.sh` и подключает `test:integration` в `check`; **M3** добавляет `scripts/sync-conflict-test.sh`; `test:integration` подключает скрипты только существующие. ## D11: жизненный цикл `machine.key`

Дата/итерация: i0
Решение: `machine.key` (32 байта, 600, `~/.local/share/secrets/machine.key`) создаётся: (1) при `secrets login`, до первого pull; (2) при первой **локальной записи** (`set`/`rm`/`mv`), если файла нет **и** локального кэша с зашифрованными данными нет. Если ключа нет, а кэш/get/export существуют — это hard error: код возврата ≠ 0, stdout пуст, в stderr — указание на `login --reset-key`. `login --reset-key` генерирует новый ключ, **выбрасывает нечитаемый кэш** (не пытается «спасти») и заново забирает вольт с сервера. Тихий автоген ключа при наличии кэша запрещён.
Альтернативы: (а) всегда автогенерить ключ при отсутствии (кэш становится нечитаемым молча); (б) хранить ключ в keyring.
Почему: §5 + тест-план §11 («нет `machine.key` → exit ≠ 0 и внятная ошибка; `login --reset-key` поднимает кэш»). Автоген при существующем кэше — это молчаливая потеря всех значений и одновременно перезапись шифртекста, то есть ровно тот класс сбоя, который §4.6 считает худшим.
Если станет неприемлемо: ключ из keyring/файла с паролем — меняется только слой `internal/config`, формат БД не меняется.
Затронутые пункты спеки: §1, §5, §11.

## D12: AAD — schema ID v1, `local|secrets/v1|path` на клиенте

Дата/итерация: i0
Решение: AAD = `"secrets/v1|" + path` на сервере и `"local|secrets/v1|" + path` на клиенте. Строка `secrets/v1` — обязательный префикс-версия: смена схемы шифрования = смена префикса, старый шифртекст тогда не расшифровывается «частично». Один хелпер в `internal/crypto` строит AAD, обе стороны зовут его.
Альтернативы: (а) AAD без версии (`secrets|path`); (б) хранить schema ID в метаданных рядом с записью.
Почему: §1 требует AAD, привязывающий шифртекст к path, и запрет на перестановку между клиентским и серверным шифртекстом. Версия в AAD даёт явный отказ вместо невнятной ошибки GCM при будущей смене схемы; отдельное поле в БД — лишняя колонка в каждой таблице. Тест «AAD-префикс `local|` ломает несовместимую запись» из гайда §3.2 опирается именно на этот формат.
Если станет неприемлемо: `secrets/v2|`, с явной миграцией и записью здесь; порядок полей (local| → schema| → path) сохранить.
Затронутые пункты спеки: §1, §2.

## D13: mapping `export` и фикстуры

Дата/итерация: i0
Решение: `export` строит имя переменной из path: uppercase, символы `/`, `.`, `-` → `_`, остальные символы алфавита пути (цифры, `_`) — как есть. Коллизия (два разных path дают одно имя, например `a/b` и `a.b`) — **ошибка**: код ≠ 0, stdout пуст, в stderr — оба path. Пустой кэш (нет ни одного значения) — тоже код ≠ 0 и пустой stdout: пустой export в `eval` выглядит как успех и молча теряет ключи (§5, КРИТИЧНО для `eval`). `--prefix P` подставляет префикс к имени до uppercase. Фикстуры и тесты, эмулирующие `.zshenv`, используют только синтетические имена (`SKS_FIXTURE_*`) и значения-маркеры — реальные значения `~/.zshenv` в репозиторий, логи и эту запись не попадают никогда (гайд §5.2).
Альтернативы: (а) коллизия → последний выиграл; (б) счётчик суффиксов `_2`; (в) сохранить `/` в имени.
Почему: `eval` не умеет сообщать об ошибке — контракт держится только кодом возврата и пустым stdout (§5, §6). «Последний выиграл» — молчаливая потеря ключа; суффиксы ломают идемпотентность между машинами (у одной коллизия есть, у другой нет). mapping, обратный к `set`, невозможен, поэтому он односторонний и объявлен явно.
Если станет неприемлемо: `--format json`/`shell` сохраняют исходные path без mapping; коллизии можно разрешать явным `--map path=NAME`.
Затронутые пункты спеки: §6, §11, §12 (M1).

## D14: `config.toml` — канонический источник url и node_id; `local_meta` хранит курсор/HLC/токен

Дата/итерация: i0
Решение: `~/.config/secrets/config.toml` — единственный дом для `url` и `node_id`; их пишет `login`. `local_meta` в `cache.db` хранит `last_seq`, `hlc_last_ms`, `hlc_counter`, `token_enc` + `token_nonce` и **не** дублирует `url`/`node_id`. При расхождении (url в конфиге ≠ url, с которым шёл синк) клиент не угадывает: ошибка с указанием `login`.
Альтернативы: (а) хранить url/node_id в `local_meta` (как перечислено в §5) и не иметь config.toml; (б) хранить и там, и там.
Почему: §5 перечисляет url/node_id в `local_meta`, но §5 же заводит `config.toml` для «url сервера, node_id (не секреты)». Два места = два источника правды при copy/restore БД: `cache.db` можно восстановить из бэкапа машины A на машину B, и тогда node_id из БД перетрёт личность B. `config.toml` не бэкапится с кэшем и читается человеком.
Если станет неприемлемо: url/node_id переезжают в `local_meta` (мультивольт на машину); читать тогда надо из БД, а config.toml оставить только для дефолта.
Затронутые пункты спеки: §5, §6.

## D15: рецепт SQLite — права, PRAGMA на соединение, один writer, `change_id UNIQUE`

Дата/итерация: i0
Решение:
- каталоги (client `~/.local/share/secrets/`, server `~/apps/secrets/data/`) — 0700; сам `cache.db`/`secrets.db` и `machine.key`/`vault.key` создаются/дожимаются до 0600 явно (предсоздание файла ключа, а не надежда на umask);
- PRAGMA (`journal_mode=WAL`, `busy_timeout=5000`, `synchronous=NORMAL`, `temp_store=MEMORY`) применяются **на каждом соединении** через DSN modernc (`?_pragma=...`), а не одним `db.Exec` после `sql.Open`; отдельный тест из гайда §3.2 проверяет `temp_store` на соединении, взятом из пула;
- запись — один writer: `SetMaxOpenConns(1)` для M1 (как уже сделано) и один writer-путь для сервера (§8: мьютекс или канал в одну горутину), write-транзакции — `BEGIN IMMEDIATE`;
- серверная схема к §2 добавляет `changes.change_id TEXT` + `UNIQUE` — без этого правило идемпотентности §4.1 («`change_id` уже применён → 200 без изменений») невыразимо; это расширение §2, и оно должно попасть в §2 при первой правке спеки, а не остаться только в коде.
Альтернативы: (а) PRAGMA один раз на пуле; (б) несколько писателей с retry на `SQLITE_BUSY`; (в) отдельная таблица `applied_change_ids`.
Почему: `temp_store` не наследуется новыми соединениями — это прямой путь к plaintext на диске, то есть провал теста no-plaintext (§1, §11). Один writer + `BEGIN IMMEDIATE` — рекомендованный режим SQLite и уже заявлен в §8. Отдельная таблица под идемпотентность дублирует `changes` и требует уборки; `UNIQUE` на `changes` закрывает и ретраи, и гонку.
Если станет неприемлемо: пул писателей с retry и WAL — точечная замена `store.Open`; колонка `change_id` остаётся.
Затронутые пункты спеки: §2, §5, §8, §11; гайд §3.3.

## D16: конфликты — API `GET /v1/conflicts`, `POST /v1/conflicts/<id>/resolve` и одна функция mapping

Дата/итерация: i0
Решение: к эндпоинтам §8 добавляются `GET /v1/conflicts` (список неразрешённых: path, reason, mine/theirs версии + значения) и `POST /v1/conflicts/<id>/resolve` (тело: `keep: mine|theirs|both`, `version` резолва). Сопоставление «сторона клиента ↔ mine/theirs» живёт в одной функции в `internal/api` (`MineTheirs(perspective NodeSide, serverValue, clientValue …)`), покрытой отдельным тестом: у клиента и сервера поля `mine`/`theirs` означают разные вещи, и это единственное место, где это переводится. `--keep both` создаёт вторую запись `<path>.<node_id>` (ничего не теряем, §6). Все три исхода пишутся в `secret_history` с `op=resolve`, `conflicts.resolution` заполняется, `integer conflict=1` на path снимается только когда неразрешённых конфликтов по path не осталось.
Альтернативы: (а) только pull-список без resolve-эндпоинта (клиент «резолвит» следующим set); (б) одна ручка `POST /v1/sync` с полем `resolution`.
Почему: `secrets resolve` (§6) — команда с явным выбором стороны; без серверной ручки клиент применяет резолв как обычный set и стирает `theirs`-версию из `conflicts`, теряя данные. Отдельные ручки делают конфликт видимым и проверяемым (тест edit/edit из §11 требует «оба значения живы»). mapping в одном месте — потому что ошибка здесь = молчаливая перезапись секрета (§4.6).
Если станет неприемлемо: резолв уходит в `POST /v1/sync` отдельным op'ом; функция mapping остаётся одна.
Затронутые пункты спеки: §4, §6, §8, §11.

## D17: `mv` — re-encrypt через `set(new)` + `rm(old)`, серверного rename нет

Дата/итерация: i0
Решение: `secrets mv <old> <new>` читает значение из кэша, шифрует его заново под AAD нового path, пишет `set(new)` и `rm(old)` — два change'а в outbox. Отдельного серверного «rename»-эндпоинта нет. Если по `<new>` уже есть запись или по пути прилетает конфликт — работает обычная конфликтная модель D16, ничего не перезаписывается молча.
Альтернативы: (а) серверный `POST /v1/mv` с atomic move; (б) `set(new)` без `rm(old)`.
Почему: AAD привязан к path (D12), поэтому перенос обязан быть перешифровкой, а не копированием блоба. Серверный rename требует новой транзакции/эндпоинта и своей семантики конфликтов на двух путях сразу; при этом он не даёт атомарности для клиента, который всё равно офлайн-первый (§5). Два change'а в outbox идемпотентны по `change_id` (D15).
Если станет неприемлемо: серверный mv с отдельным `op=mv` в `changes` и резолвом по двум path.
Затронутые пункты спеки: §4, §5, §6.

## D18: enroll-токен в stdout — единственное исключение из политики «секретов в выводе нет»

Дата/итерация: i0
Решение: одноразовый enroll-токен печатается в stdout **только** при старте `secretsd serve` без валидных токенов и только когда сервер слушает loopback (D4) с флагом `--require-enroll-token`. JSON-lines логи остаются в stdout по §8, но bootstrap-токен выводится отдельной строкой и никогда не передаётся логгеру; ни одна лог-строка не содержит токен или значение (§1, §8). После первого успешного enroll токен недействителен. Токен не попадает в `DECISIONS.md`/`ATTEMPTS.md`/репозиторий (гайд §5.2). Это осознанное исключение из общего правила «в stdout только значения/экспорты» — ровно одно и только на bootstrap-пути.
Альтернативы: (а) печатать enroll-токен в stderr; (б) `secretsd token add` до первого старта; (в) запись в файл.
Почему: §8 требует именно stdout — это единственный канал, на который оператор смотрит при первом старте, и исключение узкое: loopback + флаг + невалидные токены. Постоянного админ-токена «первый=админ» нет, и это закрывает питфолл, названный в §8.
Если станет неприемлемо: (б) — токен создаётся офлайн-командой, bootstrap-вывод убирается; политика вывода становится безысключительной.
Затронутые пункты спеки: §1, §5, §8; гайд §5.2.

Дата/итерация: i0
Решение: M4 создаёт `deploy/` с содержимым юнита (`secrets.service`, хардненинг из §10), сниппетом Caddy и документированной командой установки. ## D21: export выдаёт только валидные POSIX-имена окружения

Дата/итерация: i1 (M1)
Решение: mapping D13 обязан дать имя `[A-Z_][A-Z0-9_]*`. Если путь после uppercase и замены `/.-` на `_` начинается с цифры, `export` завершается с кодом 1 и пустым stdout; пользователь может задать `--prefix`, который сам обязан соответствовать `[A-Za-z_][A-Za-z0-9_]*` и добавляется перед mapped-именем. Коллизия имён остаётся ошибкой.
Альтернативы: (а) молча добавлять `_`; (б) выпускать невалидное имя и полагаться на shell; (в) разрешить произвольный prefix и санитизировать его.
Почему: молчаливое добавление символа делает mapping неочевидным, а невалидное имя ломает критический контракт `export | sh -n`. Явная ошибка сохраняет пустой stdout и позволяет исправить имя через контролируемый prefix.
Если станет неприемлемо: зафиксировать автоматический `_` как новую версию mapping и добавить миграционный вывод `doctor`; существующие path в БД менять не нужно.
Затронутые пункты спеки: §5, §6, §11; DECISIONS D13.
